日期：2026-09-07。以下记录本次实际开发与验证过程；小组成员的理解与分工需由本人补充，不代写尚未发生的学习经历。

| 目标 | 实际提示/检查重点 | 初始问题 | 迭代与证据 |
|---|---|---|---|
| 把模型接入业务 | “模型输出不能包含后端拥有的费用、地点快照和路线” | 直接解码共享 Plan 结构会接受这些字段 | 改为供应商专用窄结构，测试拒绝虚构后端字段及尾随 JSON；见 provider-review.md |
| 保证任务不会迟到覆盖 | “租约到期后的保存必须被拒绝” | PostgreSQL now() 固定在事务开始时间，等待行锁后仍可能允许过期保存 | 保存改用 clock_timestamp()，真实 PostgreSQL 测试持锁 350ms、租约 200ms，修复前失败、修复后通过 |
| 保护局部修改边界 | “替换活动使用新 ID 也不能绕过边界费用保护” | 按替换前活动 ID 比较会丢失边界匹配 | 用范围外不变端点作为匹配依据，测试边界费用改变时拒绝；见 core-review.md |
| 正确区分用户错误与依赖故障 | “数据库不可用不应导致前端丢弃有效会话” | 查询错误一律映射为 401 | 仅无对应记录返回 401，连接故障为 503、超时为 504；关闭数据库连接池回归测试通过 |
| 取消请求不占据未来地图配额 | “一批取消请求结束后，新请求应及时获得容量” | 预先占用的未来限流时隙未被释放 | 仅在实际放行时更新下次时隙，取消等待不占容量；取消突发回归测试通过 |
| 修复真实规划的交通留白 | “连续留白不能由 meal/rest/hotel 占用时间替代” | 首次真实生成两轮后因交通空档不足失败，原提示词只笼统要求 travel buffers | 明确连续空档及 300 秒缓冲；校验反馈包含活动标题、时间边界、实际空闲与所需秒数；后续真实一日生成通过。无法由早期日志确认模型具体如何占用了空档 |
| 对齐局部模型输出 | “editable_item_ids 才是被替换集合，时间窗只是合法边界” | 提示词容易把窗内未选中的活动也当作需要返回的对象；完整生成与局部替换规则混杂 | 明确未选中和锁定活动由后端保留，局部输出只含替换集合；完整与局部输出要求分别描述；见 provider-report.md |
| 压缩模型修复输入 | “删除重复地点快照和地图折线，保留规划证据” | 修复输入从约 7 千 Token 增至 2 万以上，出现 60 秒调用超时 | 上下文投影保留活动、费用、路段耗时；合成测试 7,840→445 字节且原对象不变；实际延迟另行实测 |
| 对齐真实公交格式 | “用真实公开响应建立回归 fixture” | 公交及接驳步行 polyline 是嵌套对象，字符串结构使整包解析失败 | 专门处理两种折线格式，按步行→公交顺序拼接，并避免把备选公交线路串联；费用与耗时保持供应商整条方案值 |
| 处理无公交方案 | “只有明确无公交方案才允许一次实查短步行” | 两个景点间可能没有公交方案；直接失败无法利用已有修复流程 | 增加 1,500 米且 25 分钟双阈值；仍无路线则反馈模型至多修复一次。鉴权、配额、超时等错误不伪装成无路线；见 final-review.md |
| 根据实测设置执行期限 | “模型、RPC 和任务期限须有一致的包含关系” | 七日模型调用触发原 60 秒超时 | 统一配置为 120 秒模型、130 秒 RPC、300 秒任务，测试验证配置关系及实际数据库领取任务的期限；HTTP 仍立即返回 202 |
| 让轻松行程留出真实交通时间 | “先选少而近的景点，缺少路线证据时留出更宽裕的连续空档” | 真实三日样例两轮后仍有 30 分钟空档不足以容纳 39～66 分钟路线 | v6 对 relaxed/balanced/intensive 建议每天 1～2/2～3/3～4 个景点；90 分钟是无路线证据时的软建议，实际路线仍按耗时加 300 秒，且不覆盖停留时长或修改范围 |

## 邮箱验证码注册与邮箱密码登录

用户确认使用 QQ SMTP，要求先完成后端并提供前端文档。保留三进程架构与既有会话机制，采用真实 PostgreSQL 测试；邮件边界使用本地 TLS SMTP 接收器，未发送真实邮件。

| 目标 | 实际检查重点 | 发现的问题 | 迭代与证据 |
|---|---|---|---|
| 邮箱验证后才能创建账号 | 注册必须同时提供邮箱、密码、challenge_id 和验证码 | 原用户名注册没有邮箱所有权证明 | 增加 HMAC 验证码、发送状态、有效期与错码上限；错码、重放、重复邮箱和并发注册测试通过 |
| 保留旧账号数据 | 旧用户名密码认证后再绑定邮箱，不新建替代账号 | 直接切换登录字段会使旧账号无法登录 | 增加受限迁移会话与绑定接口，保留 ID/角色/密码/行程；跨账号和并发绑定回归通过 |
| 防止认证额度被恶意耗尽 | 账号已超限时是否仍消耗全局/IP 额度 | 独立审查发现拒绝路径仍提交了前面限流桶的增量 | 先复现失败测试，再使拒绝路径整体回滚；登录与发信回归均通过，正常放行的失败认证仍记次 |
| 安全执行数据库升级 | 重启不能重复执行会阻塞业务的 DDL | 实测 users 的 DDL 锁与 planning_jobs 写入出现锁顺序冲突 | 将用户列迁移提前并增加版本记录；旧 schema 保留和持锁重启迁移测试通过 |
| 保持 RPC 兼容 | 新字段追加不能重排原 Thrift 编号 | 原生成器依赖结构体字段顺序编号 | 保存现有字段 ID，拒绝不兼容类型变化；2 项生成器回归通过，21 个生成相关文件重复生成无变化 |
| 认证响应不缓存 | 包括解析失败和缺失 Bearer 的早返回 | 初版只在正常 RPC 调用前设置 no-store | 先复现错误响应缺少头部，再将策略移至 auth/me 路由中间件，回归通过 |
| 对接前端 | 明确注册后登录、倒计时、重发失败与迁移提示 | 旧请求体与登录交互已不匹配 | 更新 OpenAPI、TypeScript 和 HTTP 示例；23 路径/24 操作/232 个本地引用校验通过，FE 未修改 |

最终 `go test -race ./... -count=1`、`go vet ./...`、本机与 Linux arm64 编译通过。完整 HTTP/Kitex/PostgreSQL/本地 TLS SMTP 回归 12 项通过；独立复审未发现阻塞项。本机 API/Travel 已更新并检查就绪和新路由，未提交或推送代码。

### 用户追加前端适配

后端交付后，用户要求直接修改对应前端，并明确去掉用户名迁移入口。沿用现有页面样式，邮箱登录/注册、验证码倒计时、既有未验证会话补全和账号缓存隔离一并接入。先运行 6 项新页面测试，旧页面因缺少邮箱输入/绑定页而失败；实现后扩大为 10 项页面测试，连同 API/缓存等既有测试共 45 项通过。实际浏览器确认登录页只有邮箱登录与注册入口，错误登录提示由本机真实后端返回。构建通过，未发送真实邮件。

前端独立审查发现三个会话竞争问题：业务请求401没有清理过期凭据、旧/me响应覆盖已绑定状态、迟到注销误清新会话。新增回归均先失败；分别通过请求token匹配、绑定时取消旧查询、注销完成时核对原token修复。复审通过；成功重发还会清掉旧验证码输入，失败重发继续保留有效旧证明。
