# Provider implementation report

Implemented the bounded Amap and GLM adapters in `internal/providers` using only the Go standard library.

## Amap

- Place search emits the required v5 query for scenic attractions (`110000`) and museums (`140100`), applies defaults and page bounds, validates provider status, filters the exact result whitelist by requested city and coordinates, deduplicates IDs, and maps provenance fields without treating average spend as a ticket fee. Museums receive application-category tags `室内` and `博物馆`; these tags do not claim that a venue is currently open.
- Walking and transit routing validate GCJ-02 coordinates, parse distance/duration and exact yuan-to-cent transit fees, preserve absent transit fees as unknown, join real step polylines, and reject missing or malformed routes.
- Public Amap v5 diagnostics showed transit `walking.steps[*].polyline` and `buslines[*].polyline` may be nested as `{"polyline":"coordinates"}` rather than strings. A field-specific decoder now accepts both representations plus null/missing values, while rejecting malformed object shapes. Transit geometry follows each segment's travel order (walking then bus) and selects only the first busline because remaining buslines are parallel alternatives. Whole-transit distance, 2,406-second duration, and 2.0-yuan fee continue to come from the selected transit result rather than being accumulated from segments.
- Transit fee parsing accepts only nonnegative ASCII-decimal yuan values with at most two fractional digits and checks cent conversion for `int64` overflow. Regressions reject `-1`, `1.-1`, and `92233720368547758.08`; absent fees still remain unknown (`nil`) rather than becoming zero.
- Requests use bounded responses, bounded errors, no redirects, no automatic retries, and a fallback timeout.

## GLM

- Generate and revise each make one non-streaming JSON-mode call with the required model defaults, response format, reasoning effort, token cap, trusted constraints, and revision scope instructions.
- The serialized request uses a dedicated DTO that omits the `service_token` key entirely; provider failures expose only bounded domain errors.
- Responses decode through a narrow provider DTO, so model-supplied routes, costs, and place snapshots are rejected before mapping into domain types. Parsing requires exactly one JSON value and rejects trailing content.
- Responses validate choice count, finish state, refusal/tool calls, raw-content size, narrow schema fields, output outcome, activity IDs, windows, and activity kinds. Full itinerary business validation remains in the Travel/domain layer. Invalid or truncated model output becomes `invalid_output` with bounded raw output rather than an API error.
- Model metadata records request/model identity, prompt version, elapsed time, usage, and finish reason; reasoning content is never decoded or returned.
- Missing usage fields remain unknown (`nil`) rather than being inferred as zero. The prompt treats the request instruction as desired travel preferences subject to system constraints and revision scope. It recommends Chinese response text and requests at least one sight and meal per day plus sightseeing blocks of at least 90 minutes unless candidate duration metadata says otherwise.
- Prompt version `travel-planner-v6` makes the route timing contract explicit: when route duration is known, consecutive travel activities need an unoccupied continuous gap of exactly route duration plus 300 seconds, and meal/rest/hotel blocks cannot count as that gap. Without route data, it asks the model to use candidate longitude/latitude for geographic proximity and, when the allowed window permits, aim for at least 90 minutes of continuous unoccupied travel time. The 90-minute value is explicitly a soft conservative recommendation and cannot alone make a constrained revision unsatisfied. Repair runs use the prior candidate's IDs, titles, times, and order.
- Pace density is guidance rather than a relaxed validator: relaxed prefers 1–2 sights/day, balanced 2–3, and intensive 3–4, while the existing hard maximum of five and all backend validation remain unchanged. Route repair prioritizes fewer editable sights, closer candidates, reordering, or start-time movement inside the allowed window; it forbids shortening known stay requirements or crossing scope boundaries.
- Revision output is the complete replacement for the exact `editable_item_ids` set. Locked and unselected base activities remain backend-preserved even when they lie inside the same time window; the date/start/end window only bounds legal replacements. Request projection was intentionally left unchanged in this iteration so live verification can isolate the prompt change.
- The opt-in live smoke probe uses day two when available (day one for a one-day trip), selects all activities wholly inside 12:00–20:00, and falls back to that day's full window only when the afternoon selection has no sight. It requires at least one selected sight, at least one new replacement, complete removal of selected IDs, byte-for-byte preservation of every unselected activity, scope-valid replacement dates/windows, fresh replacement IDs, and an actual museum result.

Observed follow-up evidence: a real v2 one-day generation succeeded, while both revision responses finished normally but were classified as `INVALID_MODEL_OUTPUT`. Source review found two deterministic contract conflicts: the prompt did not show a valid plan-free `unsatisfied` response, and full-generation coverage rules appeared to apply to scoped revisions. Prompt v3 now gives separate legal candidate and unsatisfied JSON examples, limits day/meal/hotel coverage to Generate, and explains that Revise returns only replacements before backend merge and full-plan validation. Invalid output issues now use a fixed bounded taxonomy for malformed JSON, unsupported fields, trailing JSON, candidate/unsatisfied shape, activity identity/window, and activity kind. These issues never include request data, secrets, provider messages, or reasoning content.

Real v3 evidence then showed a three-day Generate repair returning only the conflicting day, causing deterministic missing-day validation errors. The adapter now injects an immutable `operation` value (`generate` or `revise`) into model request data. Every Generate call, including repair, explicitly requires the complete plan for all dates with unchanged activities and forbids patches or a single conflicting day. Revise retains the exact editable-ID replacement contract. TDD RED showed both operations were absent; GREEN passed after the v4 operation projection and branch-specific instructions were added. No retry count, business validator, general data projection, or provider call behavior changed.

Real v4 evidence showed the initial three-day call completing with 7,089 prompt tokens, while the repair call exceeded 60 seconds without usage metadata; earlier repair calls had grown to roughly 20k–22k prompt tokens. Prompt v5 projects Base and any directly parseable prior `domain.Plan` into repair-only fields: activity identity/date/time/kind/place ID/title/reason/costs and route endpoint IDs/date/mode/duration/distance/fee. It removes hydrated Place snapshots, provider metadata, queried timestamps, summaries, locations, and polyline. Candidate Places remain unchanged. Unparseable or wrapped prior model text retains its original representation, bounded to 4,096 bytes. A synthetic 1,000-point polyline fixture reduced PreviousOutput from 7,840 to 445 bytes while preserving repair timing, cost, and route-duration evidence; the same test confirms the input plan is unchanged.

The live smoke probe accepts `--transport walking|transit`, defaults to walking, applies the selected transport to constraints, and records it in the report. This enables a separate multi-day transit acceptance run without weakening validation or treating provider failure as success.

Real runs established that three-day and seven-day generation can succeed, while a later three-day baseline failed after repair because 30-minute gaps were below observed 39/53/66-minute route needs. TDD RED showed the pace-specific density and conservative no-route gap/repair guidance were absent; the focused v6 prompt tests passed GREEN after adding them. This is a bounded planning heuristic change, not evidence that every route set is feasible.
